# Protocol

> Status: draft. The first implementation will refine this document, but the versioning rules should be treated as stable.

## Transports

Toget uses two transports:

| Transport | Used for | Auth |
| --- | --- | --- |
| **HTTPS + JSON** | CRUD, queries, file uploads, auth | Browser session cookie or bearer token |
| **WebSocket + JSON-RPC 2.0** | Live events, daemon commands, approvals, presence | Short-lived token in the first message, or a session cookie |

The HTTP API is described by `api/openapi.yaml`. WebSocket messages are described by the JSON Schemas in `api/events/`.

## Base URL and versioning

- HTTP base: `/api/v1`
- WebSocket: `/api/v1/ws` (web client) and `/api/v1/daemon/ws` (daemon)
- The protocol major version is negotiated in the WebSocket handshake.
- Within a major version:
  - new event types and new optional fields are allowed;
  - existing fields are not removed or renamed;
  - existing semantics are not changed.
- A breaking change requires a new major version and a documented overlap period of at least six months.

## Authentication

### Web client

1. The user signs in with GitHub OAuth or an email magic link.
2. The server sets a refresh token in an `HttpOnly`, `Secure`, `SameSite=Lax` cookie.
3. The web app keeps a short-lived access token in memory.
4. The WebSocket handshake uses the access token (or the session cookie for same-origin deployments).

### Daemon

1. The web app displays a one-time pairing code.
2. The daemon calls `POST /api/v1/devices/pair` with the code and its public metadata.
3. The server returns a device ID and a long-lived device credential.
4. The daemon stores the credential in the OS keychain.
5. The daemon uses the credential to obtain short-lived access tokens and to open `/api/v1/daemon/ws`.

Device credentials are revocable from the web app. Revocation closes the daemon WebSocket and invalidates future token requests.

## Event envelope

Every event has the same envelope:

```json
{
  "id": "0192f3c4-7a1e-7c3b-9f10-2b3c4d5e6f70",
  "room_id": "0192f3c4-7a1e-7c3b-9f10-2b3c4d5e6f71",
  "sequence": 42,
  "type": "tool.requested",
  "actor": {
    "kind": "agent",
    "id": "0192f3c4-7a1e-7c3b-9f10-2b3c4d5e6f72"
  },
  "created_at": "2026-10-30T14:00:00Z",
  "payload": {},
  "prev_hash": "sha256:...",
  "hash": "sha256:..."
}
```

- `id` is a UUIDv7, generated by the producer. It is globally unique and roughly time-ordered.
- `sequence` is assigned by the server per room. It is the ordering key for the room timeline.
- `actor.kind` is one of `user`, `agent`, `daemon`, `system`.
- `prev_hash` and `hash` form an optional hash chain. Hosted deployments enable it by default; local mode may disable it for speed.
- Unknown fields must be preserved by relays and ignored by clients that do not understand them.

## Commands

WebSocket messages use JSON-RPC 2.0. The server accepts commands from web clients and daemons; the set depends on the authenticated role.

### Web client commands

| Method | Purpose |
| --- | --- |
| `room.subscribe` | Subscribe to a room's event stream from a sequence |
| `room.unsubscribe` | Stop receiving a room's events |
| `task.create` | Create a task |
| `task.cancel` | Cancel a task |
| `approval.decide` | Grant or reject an approval |
| `agent.list` | List agents visible to the user |
| `presence.ping` | Keep the connection alive |

### Daemon commands

| Method | Purpose |
| --- | --- |
| `daemon.hello` | Register the daemon and negotiate protocol version |
| `daemon.heartbeat` | Report liveness and resource usage |
| `agent.register` | Register an agent runtime |
| `agent.unregister` | Remove an agent |
| `event.append` | Append one or more events to a room |
| `event.ack` | Acknowledge server-delivered events |
| `tool.execute` | Execute an approved tool call |
| `task.cancel` | Stop a running task |

### Server notifications

| Method | Purpose |
| --- | --- |
| `event.created` | A new event was appended to a subscribed room |
| `task.assigned` | A task was assigned to this daemon |
| `approval.requested` | A human decision is needed |
| `approval.decided` | An approval was granted or rejected |
| `agent.command` | Start, stop, or reconfigure an agent |
| `device.revoked` | The device credential is no longer valid |

## Request and response example

```json
{"jsonrpc": "2.0", "id": "c1", "method": "task.create", "params": {
  "room_id": "0192...71",
  "title": "Prepare the weekly report",
  "agent_id": "0192...72"
}}
```

```json
{"jsonrpc": "2.0", "id": "c1", "result": {
  "task_id": "0192...73",
  "event_id": "0192...74"
}}
```

Errors follow JSON-RPC 2.0 with a structured `data` object:

```json
{"jsonrpc": "2.0", "id": "c1", "error": {
  "code": -32010,
  "message": "approval_required",
  "data": {"approval_id": "0192...75", "action_digest": "sha256:..."}
}}
```

## Ordering, delivery, and idempotency

- The server assigns `sequence` per room in a single transaction with the event insert.
- Clients resume with `room.subscribe { after: sequence }`.
- Event appends are idempotent by event `id`. A duplicate ID returns the existing event.
- The daemon keeps an outbox in SQLite. If the connection drops, it reconnects and replays unacknowledged events.
- Delivery is at-least-once. Consumers must deduplicate by event ID.
- Slow consumers are disconnected when their queue exceeds a configured limit; they can resume from their last sequence.

## Approval binding

An approval is bound to the exact action it authorizes:

- The daemon computes an `action_digest` over the canonical action (tool, target, parameters, amount, recipient).
- `approval.requested` includes the digest.
- `approval.granted` includes the same digest.
- The daemon refuses to execute if the digest does not match.

This prevents an agent from requesting approval for a harmless action and then executing a different one.

## Security requirements

- All production traffic uses TLS.
- WebSocket handshakes validate the `Origin` header for browser clients.
- Rate limits apply per user, per device, and per IP.
- Payloads have size limits; file uploads use a separate endpoint with content-type checks.
- Event payloads from agents are untrusted input. They are validated against schemas and never evaluated as code.
- The server never stores agent API keys or shell credentials.

## Compatibility

- Generated clients live in `packages/api-client` and `internal/protocol`.
- CI runs contract tests against the JSON fixtures in `test/fixtures`.
- The server supports the current and previous minor protocol versions during a rollout.
- The protocol document is part of the release; a release is not complete until the document and generated clients match.
